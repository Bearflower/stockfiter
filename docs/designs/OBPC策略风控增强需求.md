## 1. 产品概述

### 1.1 背景

OBPC 超跌反弹回踩确认策略 V2.0（代码版本 v25）在 2020-01-01 ~ 2026-04-07 的回测区间内出现严重偏离预期的结果：

| 指标 | V2.0 预期 | 实际回测 | 偏差 |
|------|----------|---------|------|
| 总信号数 | 28 | 90 | +221% |
| 胜率 | 67.9% | 23.33% | -44.57pp |
| 平均收益 | 3.28% | -3.23% | -6.51pp |
| 硬止损笔数 | - | 29 | 全部亏损 -10.23% |

**核心问题**：90 个信号高度集中在 2026 年 1-3 月的系统性下跌期（其中 2026 年 2 月单月产生 54 个信号），策略在市场系统性风险释放期间产生了大量低质量信号，导致胜率与收益严重不达预期。

**根本原因分析**：
1. 当前大盘过滤仅使用沪深 300 的 20 日均线，过于灵敏，无法有效识别系统性下跌趋势；
2. 缺少单月信号数量上限，导致信号在弱势市场过度集中；
3. 缺少评分阈值过滤，低质量信号混入推送列表，拉低整体胜率。

### 1.2 业务目标

| 优先级 | 目标 | 衡量指标 |
|--------|------|---------|
| P0 | 抑制系统性下跌期的信号产出 | 系统性下跌期信号数占比 ≤ 20% |
| P0 | 提升整体胜率至预期水平 | 回测胜率 ≥ 60% |
| P0 | 提升平均收益至预期水平 | 回测平均收益 ≥ 2% |
| P1 | 控制硬止损笔数 | 硬止损笔数占总交易数 ≤ 20% |
| P1 | 保持策略信号产出能力 | 年均信号数 ≥ 4 个 |

### 1.3 用户人群

| 用户 | 关注点 |
|------|--------|
| 策略使用者（个人投资者） | 推送信号质量稳定，避免在弱势市场接到大量亏损信号 |
| 策略维护者 | 配置参数可调，便于后续调优，无需改动代码 |
| 回测验证者 | 改进效果可通过回测脚本验证，回测结果可对比 |

### 1.4 成功指标

改进上线后，重新执行 `scripts/backtest_obpc.py` 回测，需满足：

1. 2026 年 1-3 月期间信号数 ≤ 15 个（原 90 个）；
2. 整体回测胜率 ≥ 60%；
3. 整体平均收益 ≥ 2%；
4. 硬止损笔数占比 ≤ 20%；
5. 全回测区间总信号数 ≥ 20 个（保证策略仍有产出能力）。

## 2. 用户需求

### 2.1 用户故事

**US-1：作为策略使用者，我希望在系统性下跌期间不收到或只收到极少的高质量信号，以避免在市场系统性风险中频繁止损。**

> 验收要点：2026 年 1-3 月系统性下跌期间，单月信号数 ≤ 5 个，且仅推送评分最高的信号。

**US-2：作为策略使用者，我希望每月收到的信号数量有上限，避免单月信号过度集中带来的集中性风险。**

> 验收要点：任意单月信号数 ≤ 配置的上限值（默认 12 个），超过上限后停止产生新信号。

**US-3：作为策略使用者，我希望推送的信号都经过评分筛选，低质量信号不进入推送列表。**

> 验收要点：所有推送信号的评分 ≥ 配置的阈值；弱势市场下阈值自动上调。

**US-4：作为策略维护者，我希望所有风控参数都通过 `config/config.yaml` 配置，无需修改代码即可调优。**

> 验收要点：三个改进方向的所有参数均通过配置文件控制，代码中无硬编码阈值。

**US-5：作为回测验证者，我希望回测脚本能完整模拟新风控规则，以便验证改进效果。**

> 验收要点：`scripts/backtest_obpc.py` 回测结果中应用了大盘 60 日均线过滤、单月信号上限、动态评分阈值三项规则。

### 2.2 用户痛点分析

| 痛点 | 当前表现 | 期望表现 |
|------|---------|---------|
| 弱势市场信号过多 | 2026年2月单月 54 个信号 | 单月 ≤ 12 个 |
| 信号质量参差不齐 | 所有满足形态的信号都推送 | 仅推送高质量信号 |
| 硬止损频繁触发 | 29 笔硬止损全部亏损 | 硬止损占比 ≤ 20% |
| 大盘过滤失效 | 20日均线过于灵敏 | 60日均线识别系统性下跌 |
| 参数无法调优 | 部分阈值硬编码在代码中 | 全部参数可通过配置文件调整 |

#### FR-1：增强大盘趋势过滤（新增 60 日均线）

**需求描述**

在现有大盘环境过滤（沪深 300 在 20 日均线上方）的基础上，新增 60 日均线过滤条件。当大盘指数处于 60 日均线下方时，认为市场处于系统性下跌趋势，不产生新信号。

**业务规则**

| 规则编号 | 规则描述 |
|---------|---------|
| BR-1.1 | 大盘过滤同时启用 20 日均线和 60 日均线两层过滤 |
| BR-1.2 | 当 `index_close >= MA20` 且 `index_close >= MA60` 时，允许产生信号 |
| BR-1.3 | 当 `index_close < MA20` 或 `index_close < MA60` 任一条件成立时，禁止产生信号 |
| BR-1.4 | 60 日均线过滤可独立开关（即使 20 日均线过滤关闭，60 日均线过滤也可独立启用） |
| BR-1.5 | 当指数数据不足 60 天时，跳过 60 日均线过滤并输出警告日志，不阻断扫描 |
| BR-1.6 | 大盘过滤的指数代码、均线周期均可通过配置文件调整 |

**配置参数**

```yaml
strategies:
  oversold_bounce:
    params:
      index_filter:
        enabled: true                # 大盘过滤总开关
        index_code: "000300.SH"      # 指数代码
        index_ma_period: 20          # 短周期均线（原有）
        index_ma_period_long: 60     # 长周期均线（新增）
        long_ma_filter_enabled: true # 60日均线过滤开关（新增）
```

**影响范围**

| 文件 | 修改点 |
|------|--------|
| `config/config.yaml` | 新增 `index_ma_period_long` 和 `long_ma_filter_enabled` 参数 |
| `scripts/daily_scan.py` | 第 91-112 行的大盘过滤逻辑，增加 60 日均线判断 |
| `scripts/backtest_obpc.py` | `BacktestDataLoader.build_index_ma_filter` 方法，构建 60 日均线过滤字典；`BacktestEngine._backtest_single_stock` 方法，应用 60 日均线过滤 |
| `strategy/oversold_bounce/strategy.py` | 无需修改（大盘过滤在扫描层实现，不在策略层） |

**验收标准**

| AC编号 | 验收条件 |
|--------|---------|
| AC-1.1 | 配置 `long_ma_filter_enabled: true` 时，当沪深 300 收盘价 < 60 日均线，扫描脚本输出"大盘环境不佳（60日均线过滤）"并返回空信号列表 |
| AC-1.2 | 配置 `long_ma_filter_enabled: false` 时，仅使用 20 日均线过滤，行为与当前版本一致 |
| AC-1.3 | 当指数数据不足 60 天时，输出警告日志"指数数据不足60天，跳过60日均线过滤"，扫描继续执行 |
| AC-1.4 | 回测脚本应用 60 日均线过滤后，2026 年 1-3 月期间信号数显著下降（≤ 15 个） |
| AC-1.5 | 配置文件中所有 60 日均线相关参数均可独立调整，代码中无硬编码 60 这个数字 |

#### FR-2：限制单月信号数量

**需求描述**

新增单月信号数量上限控制，当某月累计产生的信号数达到上限时，该月剩余时间停止产生新信号。信号计数以信号日期（回踩确认日）所在月份为准。

**业务规则**

| 规则编号 | 规则描述 |
|---------|---------|
| BR-2.1 | 单月信号数上限通过配置参数 `max_signals_per_month` 控制，默认值 12 |
| BR-2.2 | 信号计数维度：以信号的 `signal_date`（回踩确认日）所在自然月为统计单位 |
| BR-2.3 | 当某月累计信号数达到上限时，输出日志"本月信号数已达上限 N 个，停止产生新信号"，后续扫描跳过信号产出 |
| BR-2.4 | 单月信号计数基于已推送的信号数（保存到数据库或 JSON 文件的信号） |
| BR-2.5 | 单月上限可在运行时通过修改配置文件调整，无需重启服务（下次扫描生效） |
| BR-2.6 | 单月信号上限与现有的单股票年度限制（`max_signals_per_year: 2`）独立运作，互不干扰 |
| BR-2.7 | 回测场景下，单月信号计数按回测时间序列累计，超限后该月后续窗口不再产生信号 |

**配置参数**

```yaml
strategies:
  oversold_bounce:
    params:
      # 信号间隔控制
      signal_cooldown_days: 60
      max_signals_per_year: 2
      max_signals_per_month: 12    # 新增：单月信号数上限
```

**影响范围**

| 文件 | 修改点 |
|------|--------|
| `config/config.yaml` | 新增 `max_signals_per_month` 参数 |
| `scripts/daily_scan.py` | 在信号产出前检查当月已推送信号数，超限则跳过 |
| `scripts/backtest_obpc.py` | `BacktestEngine` 类新增单月信号计数器，在 `_backtest_single_stock` 中应用 |
| `data/database.py` | 可能需要新增 `get_signal_count_this_month` 方法（若依赖数据库统计） |

**验收标准**

| AC编号 | 验收条件 |
|--------|---------|
| AC-2.1 | 配置 `max_signals_per_month: 12` 时，任意单月推送信号数 ≤ 12 个 |
| AC-2.2 | 当月信号数达到上限后，后续扫描输出"本月信号数已达上限 12 个，停止产生新信号"日志 |
| AC-2.3 | 跨月后信号计数重置，新月份重新从 0 开始计数 |
| AC-2.4 | 单月信号上限与单股票年度限制独立运作，不相互影响 |
| AC-2.5 | 回测场景下，2026 年 2 月信号数 ≤ 12 个（原 54 个） |
| AC-2.6 | 配置文件中 `max_signals_per_month` 可调整，代码中无硬编码 12 这个数字 |

#### FR-3：动态调整评分阈值

**需求描述**

根据大盘环境动态调整信号评分阈值。在大盘弱势环境（沪深 300 在 60 日均线下方）时，提高评分阈值，只推送最高质量的信号；在大盘强势环境时，维持默认评分阈值。

**业务规则**

| 规则编号 | 规则描述 |
|---------|---------|
| BR-3.1 | 评分阈值通过配置参数 `score_threshold` 控制，代码默认值 60（确保只有高质量信号进入单月名额竞争）；配置文件中设为 0 时表示不过滤 |
| BR-3.2 | 弱势市场评分阈值通过配置参数 `score_threshold_weak` 控制，默认值 75 |
| BR-3.3 | 弱势市场判定条件：沪深 300 收盘价 < 60 日均线 |
| BR-3.4 | 当信号评分 < 当前生效阈值时，信号被过滤，不进入推送列表 |
| BR-3.5 | 阈值判断时机：在信号评分计算完成后、信号保存前 |
| BR-3.6 | 被阈值过滤的信号输出日志"信号评分 X 低于阈值 Y，过滤"，便于排查 |
| BR-3.7 | 评分阈值与单月信号上限、大盘过滤独立运作，三层风控串联执行 |
| BR-3.8 | 回测场景下，评分阈值按回测时间序列动态应用（根据当日大盘环境判断使用哪个阈值） |

**配置参数**

```yaml
strategies:
  oversold_bounce:
    params:
      # 评分阈值过滤（新增）
      score_filter:
        enabled: true                  # 评分过滤总开关
        score_threshold: 0             # 默认评分阈值（0=不过滤，代码默认值为60）
        score_threshold_weak: 75       # 弱势市场评分阈值
        weak_market_condition: "below_ma60"  # 弱势市场判定条件
```

**影响范围**

| 文件 | 修改点 |
|------|--------|
| `config/config.yaml` | 新增 `score_filter` 配置段 |
| `scripts/daily_scan.py` | 在信号产出后、保存前增加评分阈值判断 |
| `scripts/backtest_obpc.py` | `BacktestEngine._backtest_single_stock` 方法，在信号产出后应用评分阈值过滤 |
| `strategy/oversold_bounce/strategy.py` | 无需修改（评分逻辑不变，过滤在扫描层实现） |

**验收标准**

| AC编号 | 验收条件 |
|--------|---------|
| AC-3.1 | 配置 `score_filter.enabled: false` 时，评分过滤不生效，行为与当前版本一致 |
| AC-3.2 | 配置 `score_filter.enabled: true` 且大盘强势时，使用 `score_threshold` 阈值过滤 |
| AC-3.3 | 配置 `score_filter.enabled: true` 且大盘弱势（沪深300 < MA60）时，使用 `score_threshold_weak` 阈值过滤 |
| AC-3.4 | 被过滤的信号输出日志"信号评分 X 低于阈值 Y，过滤" |
| AC-3.5 | 回测场景下，弱势市场期间仅评分 ≥ 75 的信号进入交易模拟 |
| AC-3.6 | 配置文件中所有评分阈值参数均可调整，代码中无硬编码 75 这个数字 |

#### FR-4：配置参数化

**需求描述**

三个改进方向涉及的所有参数必须通过 `config/config.yaml` 配置，代码中不允许硬编码任何业务阈值。遵循项目编码标准中的"禁止硬编码"强制规则。

**业务规则**

| 规则编号 | 规则描述 |
|---------|---------|
| BR-4.1 | 所有新增参数（60日均线周期、单月信号上限、评分阈值）必须从配置文件读取 |
| BR-4.2 | 代码中不允许出现硬编码的数字常量（如 60、12、75 等） |
| BR-4.3 | 配置参数需有合理的默认值，缺失时使用默认值并输出警告日志 |
| BR-4.4 | 配置参数命名遵循现有命名规范（snake_case，语义清晰） |

**验收标准**

| AC编号 | 验收条件 |
|--------|---------|
| AC-4.1 | 代码审查通过，无硬编码业务阈值 |
| AC-4.2 | 删除配置文件中新增参数后，代码使用默认值运行不报错 |
| AC-4.3 | 配置参数命名与现有 `index_filter`、`signal_cooldown_days` 等风格一致 |

| 规则编号 | 规则描述 |
|---------|---------|

| AC编号 | 验收条件 |

#### FR-6：风控命中日志

**需求描述**

记录被三项风控规则过滤的信号信息，便于后续分析和调优。

**业务规则**

| 规则编号 | 规则描述 |
|---------|---------|
| BR-6.1 | 被风控过滤的信号输出 INFO 级别日志 |
| BR-6.2 | 日志包含：股票代码、股票名称、过滤原因、过滤规则、信号评分、信号日期 |
| BR-6.3 | 日志格式统一，便于后续日志分析 |

**验收标准**

## 4. 三层风控协同流程

### 4.1 风控执行顺序

三项风控规则按以下顺序串联执行，任一环节过滤即终止后续处理：

```
信号产出（策略层）
    ↓
[风控1] 动态评分阈值过滤（前置，避免低分信号占用单月名额）
    ↓ 通过
[风控2] 大盘趋势过滤（20日 + 60日均线）
    ↓ 通过
[风控3] 单月信号数量上限检查
    ↓ 通过
信号保存 + 推送
```

**执行顺序调整说明**：
评分阈值前置，确保低分信号先被过滤，不会占用单月名额，避免高分信号因单月上限已满而被过滤（先到先得问题）。

### 4.2 风控判断逻辑伪代码

```
function apply_risk_controls(signal, context):
    # 风控1：动态评分阈值过滤（前置，避免低分信号占用单月名额）
    if score_filter.enabled:
        threshold = score_threshold_weak if is_weak_market else score_threshold
        if signal.score < threshold:
            log("信号被评分阈值过滤")
            return FILTERED
    
    # 风控2：大盘趋势过滤
    if index_filter.enabled:
        if not (index_close >= MA20 and (not long_ma_filter_enabled or index_close >= MA60)):
            log("信号被大盘趋势过滤")
            return FILTERED
    
    # 风控3：单月信号数量上限
    if monthly_signal_count(signal.month) >= max_signals_per_month:
        log("信号被单月上限过滤")
        return FILTERED
    
    return PASSED
```

### 4.3 每日扫描与回测的差异说明

| 场景 | 大盘过滤数据来源 | 单月计数来源 | 评分阈值判断 |
|------|----------------|-------------|-------------|
| 每日扫描 | 实时从数据库获取指数K线 | 从数据库查询当月已推送信号数 | 当日大盘环境判断 |
| 回测 | 预加载指数K线构建过滤字典 | 按回测时间序列累计计数 | 按回测当日大盘环境判断 |
