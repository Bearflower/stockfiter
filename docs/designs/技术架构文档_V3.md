# 股票筛选系统技术架构文档 V3

## 1. 系统概述

### 1.1 版本定位

V3 是对 V2.x 的重构，从"单策略+单体脚本"演进为"多策略+分层架构"的可扩展系统。但实际开发走了**务实路线**，未实现设计文档中的全部理想架构模块。

核心目标：
- **可扩展**：支持新增策略而不修改现有代码
- **可复用**：引擎层、数据层、通知层为所有策略共享
- **可部署**：与 V2 项目并行运行，互不影响

### 1.2 核心变更（V2 -> V3）

| 维度 | V2.x | V3（实际） |
|------|------|-----|
| 架构模式 | 单体脚本 + 统一回测器 | 五层分层架构 + 3 容器分离部署 |
| 策略管理 | 硬编码在 backtester.py 中 | BaseStrategy 抽象基类 + StrategyRegistry 注册机制 |
| 策略数量 | 单策略（超跌反弹） | 双策略：超跌反弹 + E大指数估值 |
| 数据频率 | 仅日线 | 日线/周线/月线（klines 表新增 frequency 字段） |
| 形态检测 | PatternDetector 硬编码四步 | OversoldBounceStrategy._detect_pattern() |
| 通知机制 | 单一飞书 Webhook | 单文件三合一 NotificationService（远程优先+本地降级） |
| 信号存储 | scan_results 表 | 沿用 V2 的 scan_results 表和 push_history 表 |
| 目录结构 | 根目录散落脚本 | 按层分包 |
| 配置管理 | config.yaml | config.yaml（三节结构：global/strategies/schedule） |
| 部署方式 | 单容器 | 3 容器分离（kline / obpc / eadvisor） |

### 1.3 技术栈

- **开发语言**：Python 3.9+
- **数据存储**：PostgreSQL（与 V2 共享实例，E大估值策略不依赖 DB）
- **数据源**：Baostock（K线 + 股票列表）
- **部署方式**：Docker 容器化（3 容器分离架构）
  - `stockfilter-kline`：K线服务
  - `stockfilter-obpc`：OBPC 策略（形态扫描 + 飞书推送）
  - `stockfilter-eadvisor`：E大估值策略（指数估值 + ETF推荐 + 日报推送）
- **通知系统**：飞书机器人（remote common_service 优先，本地 Webhook 降级）
- **配置管理**：YAML 文件 + 环境变量
- **ETF 推荐**：OpenAI API

### 2.2 层间依赖关系

```
通知层 ----依赖----> 策略层 (读取 Signal 数据结构)
策略层 ----依赖----> 引擎层 (注册机制) 
引擎层 ----依赖----> 策略层 + 数据层 + 通知层
数据层 ----无上层依赖----> (独立)
E大估值策略 ----独立运行----> 不依赖引擎层、数据层（不使用 PostgreSQL）
```

**与旧版设计的区别**：
- 没有 ScanEngine 类：main.py 直接调度 scripts
- 没有 StockPoolFilter 类：过滤函数在 data/stock_list.py
- 没有 SignalRepository 类：直接使用 DatabaseManager
- 通知层单文件实现（三合一）
- 回测层已移除：回测功能移出 V3
- E大估值策略独立运行，不在引擎层注册

### 2.3 各层职责

#### 引擎层 (Engine Layer)

- `StrategyRegistry`（[registry.py](file:///Users/yl/vscode/stockfilter_v3/engine/registry.py)）：策略注册中心，单例模式
- `Scheduler`（[scheduler.py](file:///Users/yl/vscode/stockfilter_v3/engine/scheduler.py)）：多策略调度器，批量加载数据、执行分析、发送通知
- `main.py`：OBPC 策略本地开发/手动测试入口

#### 策略层 (Strategy Layer)

- `BaseStrategy`（[strategy/base.py](file:///Users/yl/vscode/stockfilter_v3/strategy/base.py)）：策略抽象基类
- `OversoldBounceStrategy`（[strategy/oversold_bounce/strategy.py](file:///Users/yl/vscode/stockfilter_v3/strategy/oversold_bounce/strategy.py)）：超跌反弹回踩确认策略
- **E大指数估值策略**（[distill_changying/](file:///Users/yl/vscode/stockfilter_v3/distill_changying)）：独立策略，不继承 BaseStrategy，不在 StrategyRegistry 中注册
  - `scripts/advisor/scheduler.py`：定时调度器（指数估值采集 + ETF推荐 + 飞书日报推送）
  - `scripts/advisor/etf_recommend.py`：ETF 推荐引擎（基于估值和趋势，使用 OpenAI API）

#### 数据层 (Data Layer)

- `DatabaseManager`（[data/database.py](file:///Users/yl/vscode/stockfilter_v3/data/database.py)）：PostgreSQL 连接管理
- `KlineService`（[data/kline_service.py](file:///Users/yl/vscode/stockfilter_v3/data/kline_service.py)）：K 线服务（三级缓存）
- `DataSourceManager`（[data/data_source.py](file:///Users/yl/vscode/stockfilter_v3/data/data_source.py)）：Baostock 股票列表
- `filter_stock_list()` / `fetch_and_cache_kline()` 等函数

#### 通知层 (Notification Layer)

- `NotificationService`（[notification/service.py](file:///Users/yl/vscode/stockfilter_v3/notification/service.py)）：单文件三合一通知服务

## 3. 数据流设计

### 3.1 每日扫描流程（OBPC 策略）

```
scripts/scheduler_obpc.py 定时触发
  |
  +-- 22:15 等待 K线更新完成（轮询 task_status 表）
  |
  +-- daily_scan.py main()
        |
        +-- Scheduler(config)
        +-- scheduler.run_all_strategies()
        |     |
        |     +-- DatabaseManager.get_stock_list()
        |     +-- KlineService.batch_load_klines()
        |     +-- for code in stocks:
        |     |     strategy.analyze(code, {'d': df}) -> Signal
        |     |
        |     +-- 按 score 排序
        |
        +-- scheduler.notify_signals()
        |     +-- NotificationService.send_signal(signal)
        |
        +-- scheduler.send_summary()
  |
  +-- 08:10 次日飞书推送（读取昨日 scan_results）
```

### 3.2 K线更新流程

```
scripts/scheduler_kline.py 定时触发
  |
  +-- 22:00 K线每日更新（update_kline_daily.py）
  +-- 更新完成后写入 task_status 表（task_name='kline_update', status='completed'）
  +-- 10:00 历史数据快速补全（quick_backfill.py）
```

### 3.3 E大估值策略流程

```
distill_changying/scripts/advisor/scheduler.py 定时触发
  |
  +-- 23:10 指数估值采集
  +-- ETF 推荐引擎计算（etf_recommend.py，使用 OpenAI API）
  +-- 飞书日报推送
  +-- (完全不依赖 PostgreSQL，独立运行)
```

## 5. 技术决策记录

### 5.1 ADR-001：为什么务实路线而非完整架构？

**决策**：先实现核心功能（基础策略+调度+通知），部分模块简化或延后。

**原因**：
1. 快速验证策略注册机制和分层架构的可行性
2. 避免过度设计，非核心模块（ScanEngine、StockPoolFilter 等）在需要时再实现
3. 单文件通知层足够当前使用，无需拆分为多文件

### 5.2 ADR-002：为什么沿用 V2 的数据库表？

**决策**：不新建 strategy_signals 表，直接复用 scan_results 和 push_history。

**原因**：
1. 减少数据库迁移工作量
2. 与 V2 数据格式兼容
3. push_history 的 (code, push_date) 唯一约束已满足去重需求

### 5.3 ADR-003：为什么通知层单文件实现？

**决策**：FeishuNotifier、NotificationService 两个类放在一个文件中。

**原因**：
1. 两个类紧密相关，拆分意义不大
2. 减少导入复杂度
3. 代码量适中（约 380 行），单文件维护方便

## 6. 非功能需求

### 6.1 可扩展性

- 新增策略：只需创建新策略子包，实现 BaseStrategy 接口，在 main.py 中注册
- 新增数据源：只需在 KlineService 中增加新的获取方式
- 新增通知渠道：在 NotificationService 中增加新的发送后端

### 6.2 可维护性

- 每层独立模块，修改影响范围明确
- 策略独立，修改一个策略不影响其他策略
- 配置驱动，参数调整无需修改代码
- 完善的日志和错误处理
