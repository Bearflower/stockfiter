# 部署日志与宿主机监控闭环设计

**目标**：纯文档提交不触发镜像构建/生产重建；每次实际发布保留可跨部署追溯的容器及服务日志；宿主机监控脚本与发布提交一致。

**范围**：GitHub Actions 部署工作流、日志代理/归档/保留脚本、三个 Dockerfile 与 Compose、宿主机 `monitor.sh` 发布辅助脚本及相应测试和文档。不改策略、行情采集或监控告警规则；本轮不自动提交、推送或部署。

## 设计决策

1. GitHub `push.paths-ignore` 同时保留根目录 `*.md`、增加 `**/*.md`，覆盖子目录 Markdown；工作流内构建判定按完整 push 范围判断，不能只看 `HEAD~1`。checkout 使用完整历史；基准提交缺失时保守构建。代码或部署文件与文档混合提交仍正常构建部署。`workflow_dispatch` 明确执行发布，不被路径过滤。发布 concurrency 排队，不取消正在运行的发布。
2. `docker/build-push-action` 给三个镜像写入提交 SHA 的 build arg、环境变量和 OCI revision label。日志代理将接收时间、容器名和镜像提交 SHA 写入每条宿主机服务日志，仍向 stdout 原样转发。新日志路径为 `logs/{kline,obpc,eadvisor}_scheduler.log`；已经存在的 `logs/services/*.log` 原样保留，不迁移或删除。
3. 旧容器在停止后、重建前归档，使用 `logs/container-archive/<UTC时间>-<run_id>-<新提交短 SHA>/`。先写临时目录，三份压缩包和 manifest 全部校验后再原子公布；失败目录不计入保留轮次。归档文件每行包含 Docker 原时间戳、容器名和旧镜像提交 SHA；首轮旧镜像无 revision label 时明确写 `unknown` 与镜像 ID，绝不从部署日志猜测。既有 `logs/container_archive/` 不删不迁移。Docker 查询失败阻断重建。Docker JSON 轮转已丢失的历史无法归档，跨部署完整历史靠持久文件日志。
4. 单独的保留脚本只识别 `container-archive` 下具有有效 manifest 的完成态目录；默认 90 天，且始终保留最近两次完整归档。只删除受管归档目录，出现未知文件则跳过目录并告警。部署成功后运行清理；归档和清理参数通过环境变量覆盖。
5. CI 从同一提交下载 `scripts/monitor.sh` 与宿主机发布辅助脚本。辅助脚本先 `bash -n`，按 PID/工作目录和父进程链精确核对顶层 `bash monitor.sh`（短暂 Bash 子进程不算第二实例），容器维护窗口前暂停监控，容器健康确认后原子替换脚本（文件相同时不改写）并启动唯一进程。新监控必须在初始化完成后写入与新 PID 一致的 `logs/monitor.ready`，再持续保持唯一进程至少 `MONITOR_START_STABLE_SECONDS`（默认 10 秒）；就绪等待上限 `MONITOR_READY_TIMEOUT_SECONDS`（默认 60 秒）。发布成功记录前再次核对 PID 与就绪标记。任何实际容器发布均需重启监控以避开维护窗口误报；纯文档提交不会进入此流程。失败恢复旧脚本与进程，但整次发布记 `PARTIAL_FAILURE` 且不得写 `DEPLOY_SUCCESS`。首次上线时旧版 `monitor.sh` 没有就绪标记协议，因此只在失败回滚旧进程时允许采用唯一 PID + 稳定存活检查；这个兼容例外不能用于新监控激活或发布成功判定。现有 `monitor.log` 不清除。
6. 三容器必须逐一通过 Docker health 状态检查，才进入监控更新；新监控核验后、写成功记录前还要立即复查三个容器当前均为 `healthy`，防止最先通过的容器在等待其余容器期间再次失效。任何失败不能由 `grep ... || echo` 转成成功；远端部署脚本必须设置 EXIT/TERM/INT 恢复钩子，至少尝试恢复旧监控，并记录失败与人工回退所需的旧镜像 ID。不能保证容器自动回滚时明确记为部分失败。

## 验收条件

- AC1：根目录及子目录纯 Markdown 提交均不触发本工作流；混合代码提交仍执行构建部署。
- AC2：连续两轮模拟发布后，第一轮前的 *Docker 当前尚保留* 日志仍可读取；三只旧容器及三份归档缺一即阻断发布；归档行包含时间、容器和旧提交 SHA（首轮无 label 的旧镜像标为 `unknown` 并记录镜像 ID），压缩包完整。
- AC3：三个服务文件持续追加、按既有大小配置轮转；每行具有时间、容器和提交 SHA；stdout 仍可用。
- AC4：保留脚本只清理 90 天前且不属于最近两次发布的受管归档，异常路径和未知文件不删。
- AC5：纯文档提交不重启监控；实际容器发布前暂停并在健康确认后恢复唯一实例，且新 PID 写出就绪标记、通过稳定观察，脚本相同不改写文件；语法错误、进程身份不明或启动失败时不留下两个实例并恢复旧版，发布结果不得记成功。
- AC6：健康检查或归档失败时不写 `DEPLOY_SUCCESS`；并发 push 不会取消中途发布。
- AC7：本地测试、YAML/Shell/编译检查通过。真实“纯文档 push 不触发”及连续两次生产发布属于发布后验收，本地只能验证配置与模拟流程。

## 发布及回退边界

首次上线会重建容器，须另行获得提交、推送、部署授权。发布前记录旧容器 ID、镜像摘要及旧监控进程 PID；发布后核对归档、持久日志、监控摘要/进程数及 `hard_filter`。若新监控发布失败，恢复旧脚本并重启旧进程，但已启动的新容器不会自动回滚：标记 `PARTIAL_FAILURE`，保留旧镜像 ID 与旧配置用于人工回退。历史上已被 Docker 删除的日志不可恢复。

**版本**：V1.0，2026-10-26。用户在本轮引用并要求落实先前整改方案，视为目标设计确认；90 天/最近两次是本轮明确的保守初值。
