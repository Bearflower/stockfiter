## 1. 背景与目标

### 1.1 背景

2026-09-29 对全仓执行了 open-code-review-delegate 代码审查（文件覆盖率 89.43%），产出 23 项可行动缺陷（R01~R23），其中原报告定级 P1/high 10 项、P2/medium 13 项。缺陷集中在四类风险面：

1. **信号风控与额度**：月度/每日额度未真正生效、扫描与推送日期错位、指数风控数据新鲜度未校验；
2. **投顾输入质量**：估值分位语义错误、持仓别名混算、LLM 输出格式/边界校验失效；
3. **数据任务可靠性**：K 线更新部分失败仍上报成功、重试分支报错、超时线程泄漏、任务入口 os._exit 中断全流程；
4. **持久化与回测可信度**：投顾知识库与 OBPC 信号目录未持久化、回测存在未来信息泄漏、成交价不可成交、净值与收益口径不一致。

另经四路独立复核智能体交叉验证，**23 项全部真实，0 误报、0 夸大，行号精确、证据可回溯**（复现脚本见 `docs/reports/code-review-2026-09-29/reproduce.py`，13 组隔离复现已锁定"缺陷仍存在"）。

### 1.2 修复目标

- **安全目标**：立即消除凭据明文暴露，轮换凭证，杜绝泄露面扩大。
- **正确性目标**：让信号额度、扫描日期、风控数据、投顾输出、数据任务上报与回测成交/净值模型恢复到符合业务语义的正确行为。
- **可靠性目标**：数据不完整时下游不得把残缺数据当完整数据；临时故障可重试、可降级、不静默丢失。
- **可维护目标**：所有阈值/评分/调度/风控参数来自 `config.yaml` 或算法计算，**禁止新增硬编码**。

### 1.3 总体验收标准（顶层口径）

1. 23 项逐项验收全部通过（见第 4 章逐项标准 + 第 6 章验收清单）。
2. 修复后，`docs/reports/code-review-2026-09-29/reproduce.py` 中的断言由"缺陷仍存在"翻转为"缺陷已修复"（改为正确行为断言），全部通过。
3. 无新增硬编码：新增阈值若尚未入 `config.yaml`，必须提取为配置项，引用前由本 PRD 审批。
4. 回测类缺陷（R07/R08/R19/R20/R21）修复前，既有回测绩效（收益/胜率/回撤）**不得作为有效性证据**；有效性以正确行为断言 + 前缀不变性检查为准。
5. 涉及数据库/部署的改动，需在本地（或按项目规范）完成验证，不得在服务器直接回测。

### R01 · 价格分位被作为 PE/PB 估值分位输出 —— 【定性：有意近似 · 业务语义缺陷】

- **问题现状**：组件估值分支把指数收盘价历史分位同时赋给 `pe_percentile` 与 `pb_percentile`（`distill_changying/scripts/advisor/market_data.py:520-523`），温度计、ETF 阈值与日报随后把它们当作估值指标消费。代码注释表明作者**有意用价格分位做估值近似**，非无意笔误。
- **定性修正**：本项由"高危 bug"修正为"业务语义缺陷"。价格分位在盈利或净资产变化时不能代表 PE/PB 分位，可能给出方向错误的估值建议，因此仍需修，但应与"无意 bug"区分对待（是否接受该近似见第 5 章待决策项 D-2）。
- **期望行为**：将"价格分位"与"估值分位"拆分为语义独立的字段/标签。若保留价格指标，必须使用独立字段（如 `price_percentile`）与独立标签，**不得再赋值给 `pe_percentile`/`pb_percentile`**；若需真实估值分位，则需计算 PE/PB 估值时间序列分位（依赖数据源是否提供 PE/PB 数据）。
- **验收标准**：
  1. `market_data.py` 输出结构中 `price_percentile` 与 `pe_percentile`/`pb_percentile` 明确分离，二者不共享赋值。
  2. `temperature.py`、`etf_recommend.py`、`daily_report.py` 消费的字段与标签和字段语义一致：估值判断只使用真实估值分位，价格分位仅用于独立展示（若保留）。
  3. 新增对 `market_data.py` 的单元测试：给定已知收盘价序列，断言输出字段的语义与标签完全匹配，价格分位不再冒充估值分位。
- **涉及文件**：`distill_changying/scripts/advisor/market_data.py`、`temperature.py`、`etf_recommend.py`、`daily_report.py` 及投顾 `config.yaml`（阈值/字段开关）。
- **依赖关系**：无强依赖；结果口径需用户拍板（见 D-2）。
- **风险**：改动影响投顾输出口径，ET 阈值/温度计的判定结果会变化，需业务确认口径。

### R02 · 月度上限未计入本批待保存信号 —— 【P1 · 与 R21 同批】

- **问题现状**：`scripts/daily_scan.py:264-271` 扫描每个候选时读取同一数据库月计数，直到扫描结束才 `save_scan_result`，`DatabaseMonthlyCounter.increment` 不增加本地计数。故已有 29 条、月限 30、日限 5 时仍新增 5 条，最终 34 条，突破下限 `max_signals_per_month`。
- **期望行为**：扫描收集完所有候选并排序后，按"剩余月度额度 = `strategies.oversold_bounce.params.max_signals_per_month` − 已用月度额度"截取最终待保存信号；保存时以数据库实际扣减结果为准，防止并发超额。日限由 `strategies.oversold_bounce.params.max_daily_signals` 独立约束。
- **验收标准**：
  1. 隔离场景 `monthly_limit`：月已用 29、`max_signals_per_month=30`、`max_daily_signals=5` 时，本次保存 1 条（而非 5 条），最终月计数 == 30（而非 34）。
  2. 并发场景（模拟多线程同时保存）下月计数不超出 `max_signals_per_month`。
  3. 新增测试覆盖"剩余额度 < 本批候选数"与"剩余额度 >= 本批候选数"两分支。
- **涉及文件**：`scripts/daily_scan.py`、`data/database.py`（`DatabaseMonthlyCounter`）。
- **依赖关系**：与 R21 同批（实盘版/回测版同一额度逻辑）。
- **风险**：额度截取若实现为"先全量再截取"，需保证排序口径与 R21 回测一致；并发扣减需依赖数据库事务或原子更新。

### R03 · 早晨重扫使用当天日期，推送却读取昨天文件 —— 【P1】

- **问题现状**：`scripts/daily_scan.py:41-46` 只按星期计算日期，盘前（07:30 补全后）也返回今天。`feishu_push` 读取 `signals_昨天.json`，重扫新增结果写入今天文件，无法进入当晨推送，且扫描日期、冷却与月计数被错记。
- **期望行为**：由调度器向 `daily_scan` 传入"本次已完成行情的交易日"，让扫描、落库、文件命名与推送共享同一交易日；盘前重扫写入的文件名与推送读取的文件名一致。
- **验收标准**：
  1. 隔离场景 `morning_scan_date`：07:30 补全完成后调用扫描，写入信号文件与当晨 `feishu_push` 读取的文件名一致，信号可被推送。
  2. 扫描日期、冷却期判定、月计数均基于传入交易日而非"今天"。
  3. 新增测试：盘前与盘后两次调用，传入同一交易日时，文件与计数不重复、不冲突。
- **涉及文件**：`scripts/daily_scan.py`、`scripts/scheduler_obpc.py`、`scripts/feishu_push.py`。
- **依赖关系**：与 R05（信号目录持久化）相关，但不阻断。
- **风险**：交易日语义需在调度器与扫描间统一传递，避免参数遗漏导致回退到"今天"。

### R04 · 投顾知识库被排除出镜像且没有挂载产物目录 —— 【P1】

- **问题现状**：`docker-compose.yml:84-88` 仅挂载 blog 与 `distilled/logs`；`.dockerignore:14` 排除了整个 `distill_changying/docs`。核心 `.state.json`、观点库、持仓及索引既未进镜像也未由宿主机提供，投顾首次运行缺知识、重建容器后重新生成的产物丢失。
- **期望行为**：将投顾完整产物目录纳入持久化并完成初始化：docker 构建上下文包含必要产物，或由宿主机挂载提供；新部署与容器重建后，既有知识可读、新产物不被丢弃。
- **验收标准**：
  1. 干净目录首次部署后，投顾能读取既有知识（`.state.json`、观点库、持仓、索引）。
  2. 容器重建后，新生成的产物仍存在（文件仍可读、内容一致）。
  3. 新增验证：模拟"空库 → 启动 → 生成产物 → 重建容器 → 再启动"的读写通过。
- **涉及文件**：`docker-compose.yml`、`Dockerfile.eadvisor`、`.dockerignore`、`distill_changying/scripts/advisor/knowledge_base.py`、`state_manager.py`。
- **依赖关系**：无强依赖。
- **风险**：`.dockerignore` 调整可能使镜像体积变化；宿主机挂载路径需与容器内读写路径对齐。

### R05 · OBPC 信号目录没有持久化 —— 【P1】

- **问题现状**：`docker-compose.yml:57-61` 扫描写入 `/app/signals`、推送也从该目录读，但只挂载 `/app/output`。晚间扫描后、早间推送前重建容器会丢失信号文件；数据库已有记录会参与去重/冷却，无法靠重扫恢复同一批信号。
- **期望行为**：挂载实际 `signals` 目录，或让推送从持久数据库重建待推送批次（二选一，以落地成本低且不破坏去重/冷却逻辑为准）。
- **验收标准**：
  1. 晚间扫描完成后、早间推送前，重建容器，信号文件仍存在且可被推送。
  2. 若采用"数据库重建待推送批次"方案，推送内容与扫描结果一致，去重/冷却判断正确。
- **涉及文件**：`docker-compose.yml`、`scripts/feishu_push.py`（若走数据库方案）。
- **依赖关系**：与 R03（日期共享）相关。
- **风险**：选型需在方案评审时确定，避免两套方案并存导致双写。

### R06 · 历史指数数据未校验新鲜度即参与当天风控 —— 【P1 · 依赖 R13】

- **问题现状**：`strategy/oversold_bounce/risk_control.py:515-516` 的 `get_context(date_str)` 直接用最后一条指数收盘价，未比较其实际日期与本次交易日，随后把 `current_date` 设为 `date_str`。指数更新失败或停止时，旧 MA/MACD 仍被视作当天风控数据；`index_update.py` 未接入默认调度链。

- **期望行为**：将业务函数与 CLI 解析分离；主入口调用可正常返回的更新函数，子函数不 `os._exit`。
- **验收标准**：`python main.py --all` 依次完成更新 → 扫描 → 推送全流程，不因参数错误或 `os._exit` 中断。
- **涉及文件**：`main.py`、`scripts/data/update_kline_daily.py`。
- **依赖关系**：无。
- **风险**：CLI 解析重构需保持既有 `--days` 调用兼容。
