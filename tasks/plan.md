# Implementation Plan: K 线采集进程隔离与断点续采

## 1. 背景与结论

2026-10-21 23:00 的主采集在连续成功 609 只后，`600859.SH` 单次请求超过 15 秒。现有实现正确地废弃了不可安全复用的 Baostock 会话，但同时终止了整批 2911 只股票，导致覆盖率停在 20.95%，23:45 初扫被 `blocked_data` 阻断；07:00 回补再将覆盖率恢复至 99.9%。

因此：

- 当前 fail-closed 行为必须保留；
- 不得恢复“超时后继续复用同一会话”；
- 不得以降低 98% 覆盖率门槛解决问题；
- 根治方向是把不可取消的 Baostock 请求隔离在可终止的子进程中，并从数据库断点继续剩余股票。

## 2. 目标与非目标

### 目标

1. 单只股票超时后，彻底结束持有损坏会话的进程。
2. 使用新进程、新会话从缺失股票继续采集，而不是终止整批。
3. 在 OBPC 初扫等待截止时间前尽量恢复至配置的覆盖率红线。
4. 多次恢复仍失败时继续 fail-closed，并保留 07:00 回补兜底。
5. 所有重试次数、分片规模、超时和截止时间均配置化并可观测。

### 非目标

- 不调整 OBPC 形态、评分或市场风控逻辑。
- 不切换 `hard_filter` / `shadow` / `graded`。
- 不降低 `min_coverage_rate=0.98`。
- 不在生产服务器运行回测或参数优化。
- 不把停牌、退市整理等长期无行情股票强行伪造成成功。

## 3. 架构决策

### 3.0 已确认的实施选项

1. **两条入口统一：** `scheduler_kline.py` 的 23:00 路径与 `main.py --all` 都调用同一个共享监督者；禁止保留可绕过监督者的全量采集入口。
2. **截止时间按消费者窗口推导：** `initial_scan_time + KLINE_WAIT_TIMEOUT - safety_buffer`，当前语义约为 23:40；不得另设绝对时刻形成双源。
3. **彻底移除 Baostock 线程池超时：** 所有公开全量入口均由监督者提供进程级超时，工作进程内部只做串行请求。
4. **允许本地只读基准：** 约 100 只股票，只访问 Baostock、不连接或写入数据库，用于确定分片和进程超时初值。

### 3.1 调度器作为监督者，采集器作为一次性工作进程

`scheduler_kline.py` 负责：

1. 计算目标交易日和初扫等待截止时间；
2. 查询目标日缺失股票；
3. 按配置将股票分片；
4. 为每个分片启动独立采集子进程；
5. 子进程超时时执行 terminate，宽限期后仍存活则 kill；
6. 重新查询数据库缺口，并用全新进程继续；
7. 覆盖率达标、触及恢复上限或到达整体截止时间时结束。

旧进程退出后，旧 Baostock socket、线程和会话一并由操作系统回收。监督者不得在进程内复用发生过超时的会话。

监督者应抽成共享模块或共享函数，由以下入口共同调用：

- `scheduler_kline.py` 的 23:00 自动任务；
- `main.py --all` 的人工/批处理入口。

`main.py --all` 通过适配层维持现有返回值、退出码和后续步骤语义，但不得再直接调用未受监督的 `run_update()`。同时应审计 CLI，确保不存在第三个可以直接发起不受监督全量采集的公开入口。

### 3.2 工作进程纯串行访问 Baostock

工作进程复用 `quick_backfill.py` 已验证稳定的模式：

- 一个进程内只建立一个 Baostock 会话；
- 串行处理当前分片；
- 不使用 `ThreadPoolExecutor` 包裹 Baostock 调用；
- 每只股票写入后立即提交/保持现有 upsert 语义；
- 返回数据必须包含目标交易日，才计为目标日成功；
- 输出结构化 result JSON，退出码表示本分片成功、部分失败或进程异常。

现有 `_fetch_with_timeout()` 及其 `ThreadPoolExecutor` 应从实际 Baostock 采集路径彻底移除，而不是只在分片模式禁用。否则旧全量模式仍会保留同类损坏会话问题。进程级超时由共享监督者统一承担。

### 3.3 数据库作为断点

不新增内存游标作为唯一断点。每次新进程启动前，重新从数据库计算目标日缺失股票：

- 已成功落库的股票自动跳过；
- 超时分片中已经完成的股票不会重复成为缺口；
- 进程被 kill 后仍可从真实数据库状态恢复；
- 数据写入继续使用幂等 upsert。

### 3.4 完成状态保持兼容

不新增会破坏下游的 `task_status.status` 枚举：

- 最终覆盖率达标：`completed`；
- 最终覆盖率不达标：`failed`；
- 通过重建进程恢复成功时，在 `details.completion_mode` 标记 `recovered_after_timeout`；
- `details` 记录分片数、会话重建次数、超时股票、覆盖率变化和耗时。

## 4. 配置设计

在 `global.kline_update` 下增加配置项，禁止散落硬编码：

- `worker_chunk_size`：单个工作进程处理的最大股票数；
- `worker_timeout_seconds`：单分片进程级超时；
- `worker_terminate_grace_seconds`：terminate 后的退出宽限期；
- `max_session_restarts`：单次主任务最多允许重建多少次会话；
- `recovery_deadline_buffer_seconds`：必须早于 OBPC 等待截止时间结束的安全余量；
- `immediate_recovery_enabled`：主采集失败后是否立即断点恢复；
- `max_consecutive_no_progress_rounds`：连续无新增数据的停止阈值。

初始值必须根据 2026-10-21 的生产耗时和本地故障注入测试确定，并写明计算依据；不得凭经验随意填写。整体截止时间应由采集开始时间、OBPC `KLINE_WAIT_TIMEOUT` 和安全余量推导，避免调度参数双源漂移。

截止时间的唯一计算公式为：

```text
collection_deadline = initial_scan_time + KLINE_WAIT_TIMEOUT - recovery_deadline_buffer_seconds
```

以当前 23:15 初扫、1800 秒等待和 5 分钟余量计算，截止时间约为 23:40。实现时必须从同一配置来源读取初扫时间和等待时长；不在 K 线配置中再次写死 `23:40`。

### 4.1 本地只读基准规范

开发前允许运行一次约 100 只股票的本地 Baostock 基准，约束如下：

- 不连接数据库、不调用任何保存函数；
- 查询字段、复权方式和历史窗口与生产采集一致；
- 样本同时覆盖沪市、深市及不同代码区段，使用固定随机种子或保存明确代码清单；
- 基准脚本自身运行在有整体超时的独立进程中，避免本地永久挂起；
- 记录运行时间、成功数、失败数、总耗时、单股 p50/p95/max 和登录耗时；
- `worker_chunk_size` 和 `worker_timeout_seconds` 的计算过程写入实施记录；
- 100 只样本只能用于初值估算，最终还必须通过故障注入和完整 2911 只的本地模拟验证。

## 5. 任务分解

### Task 1：定义工作进程与监督者契约

**内容：** 定义分片输入、result JSON、退出码和 `task_status.details` 字段，不先改主控制流。

**验收标准：**

- 契约能区分正常完成、部分失败、请求超时、进程超时和配置错误；
- result JSON 包含目标日、分片范围、成功/失败数和实际落库覆盖率；
- 旧 result JSON 消费方保持兼容。
- `scheduler_kline.py` 与 `main.py --all` 使用同一监督者契约，且保持各自现有调用方语义。

**可能涉及：**

- `scripts/data/update_kline_daily.py`
- `scripts/scheduler_kline.py`
- `tests/scheduler/test_kline_guard_and_completeness.py`

### Task 2：实现可独立终止的串行分片工作进程

**内容：** 为采集脚本增加明确的目标日与股票分片输入，移除工作进程内部针对 Baostock 的线程池超时，按串行模式处理并输出结果。

**验收标准：**

- 工作进程不创建用于 Baostock 请求的线程池；
- 旧全量模式也不得继续使用 `_fetch_with_timeout()`；
- 指定分片之外的股票不会被处理；
- 返回数据不含目标交易日时不得计为成功；
- 重复运行同一分片不会产生重复数据或破坏历史数据。

**可能涉及：**

- `scripts/data/update_kline_daily.py`
- `scripts/data/quick_backfill.py` 或抽取出的共享采集模块
- 对应单元测试

### Task 3：实现监督者的进程超时、终止和断点续采

**内容：** 调度器顺序启动分片进程；超时时终止整个工作进程，重新计算缺口并使用新进程继续。

**验收标准：**

- 故障注入在第 610 只股票超时时，旧工作进程被确认退出；
- 新工作进程从数据库缺口继续，已落库的 609 只不重复计数；
- 单次超时后最终覆盖率仍可达到配置红线；
- 重建次数耗尽或截止时间到达时必须返回失败，不能假装完成。
- `main.py --all` 与 23:00 调度路径均通过相同故障注入用例，证明不存在旁路。

**可能涉及：**

- `scripts/scheduler_kline.py`
- `scripts/data/update_kline_daily.py`
- `config/config.yaml`
- `docker-compose.yml` / `.env.example`（若调度参数由环境注入）

### Task 4：加入主任务失败后的立即恢复闭环

**内容：** 主更新进程非零退出后，不等到次日 07:00；在截止时间和恢复次数允许时立即启动缺失股票恢复流程。

**验收标准：**

- 23:00 主任务发生一次会话故障后，数分钟内开始新进程恢复；
- 恢复达标时 `task_status=kline_update/completed`，并记录 `completion_mode=recovered_after_timeout`；
- 恢复失败时保持 `failed`，23:15 初扫仍由覆盖率门禁阻断；
- 07:00 `backfill` 保持独立存在，可继续补偿前夜未恢复的缺口。

### Task 5：补齐监控和结构化诊断

**内容：** 让监控区分“主进程一次超时但已恢复”和“最终覆盖率仍不足”。三条相关 CRITICAL 可做关联降噪，但不得隐藏真实失败。

**验收标准：**

- 已恢复事件最多发一次 WARNING/INFO，不再按最终失败告警；
- 最终不达标仍发送覆盖率不足和扫描阻断告警；
- 告警包含目标日、超时股票、重建次数、最终覆盖率和 completion mode；
- `data_metrics` 缺失检查仍保持 fail-closed。

**可能涉及：**

- `scripts/monitor.sh`
- 监控回归测试

### Task 6：故障注入、集成验收与灰度部署

**内容：** 先在本地用 fake worker/受控阻塞完成故障注入，再保持 `hard_filter` 部署生产观察。

**验收标准：**

- 单次请求超时：换新进程后恢复至 ≥98%；
- 连续多次超时：达到配置上限后 fail-closed；
- 工作进程无法响应 TERM：宽限期后 KILL，且无残留进程；
- 两至三只永久无数据股票：不妨碍达到 98%，但必须列入缺失明细；
- 数据库暂时不可用：不得错误标记完成；
- 非交易日：不会误触发大规模采集；
- 相关测试、全量测试、编译检查和 shell 检查全部通过。
- 本地只读基准完成，配置初值有可复核计算依据。

## 6. 验收标准

### 功能验收

1. 第 610 只股票发生一次 15 秒级故障时，不再导致剩余 2300 只永久跳过。
2. 每次恢复都使用新的 OS 进程和新的 Baostock 会话。
3. 最终是否放行只由数据库真实覆盖率和既有完整性规则决定。
4. 任何失败路径都不得绕过 98% 覆盖率门禁。

### 时序验收

1. 单个工作进程超时后，在配置的恢复启动时限内拉起新进程。
2. 正常或可恢复的单次故障，应在 OBPC 初扫等待截止时间前达到覆盖率红线。
3. 无法恢复时必须在截止时间前明确写入 `failed`，不能悬挂三小时。

### 可观测性验收

`task_status.details` 至少能回答：

- 哪只股票/哪个分片超时；
- 创建了多少个工作进程；
- 每轮新增多少只；
- 最终覆盖率是多少；
- 是正常完成、恢复完成还是最终失败；
- 总耗时和停止原因是什么。

### 上线验收

1. 生产配置继续保持 `hard_filter`。
2. 部署后五层验证通过：容器、镜像、版本、关键文件摘要、启动日志。
3. 连续观察至少 5 个交易日：
   - 不出现三小时挂死；
   - 单次瞬时超时不会造成整批覆盖率停在低位；
   - 23:45 前覆盖率达到红线，或明确失败并正确阻断；
   - 07:00 回补从“每日必需主路径”恢复为“异常兜底路径”。

## 7. 风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 分片过小导致频繁登录 | 总耗时增加 | 依据生产单股耗时进行本地基准测试，配置化分片 |
| 分片过大导致一次超时损失进度 | 恢复延迟 | 数据库逐股落库，重启前重新计算缺口 |
| terminate 后进程不退出 | 残留连接 | 宽限期后 kill，并验证 PID 消失 |
| 重试风暴加重 Baostock 压力 | 故障扩大 | 会话重建次数、无进展轮次和整体截止时间三重限制 |
| 状态枚举变化破坏下游 | 验收/监控不兼容 | 保持 completed/failed，扩展 details 而非新增状态 |
| 夜间仍无法恢复 | 初扫无结果 | 保留 blocked_data 和 07:00 backfill，不放宽门禁 |

## 8. 实施顺序与检查点

依赖顺序：契约 → 串行工作进程 → 监督者 → 立即恢复 → 监控 → 灰度。

### Checkpoint A：Task 1–2

- 工作进程可独立执行并生成稳定 result JSON；
- 不再使用线程池包装 Baostock 请求；
- 幂等和目标日校验通过。

### Checkpoint B：Task 3–4

- 第 610 只超时故障注入完整复现并恢复；
- 无残留工作进程；
- 覆盖率达到红线或按期失败。

### Checkpoint C：Task 5–6

- 告警语义、全量测试和部署验证通过；
- 进入 5 个交易日生产观察期。
